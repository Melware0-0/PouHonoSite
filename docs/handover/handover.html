1Summary and where things stand

Pou Hono is the registration website for NZ Tech Week 2027, run by SACTH and The Cause Collective for South Auckland schools, youth groups and individuals.

A teacher registers their class and is given two things: a link and QR code to share with their students, and a private link to their own class portal. They are also sent both by email once email is switched on. Students open the shared link and register themselves, and they are grouped under their teacher's class automatically. Teachers can also type students in themselves. Individuals who are not part of a school group can register on their own. SACTH staff see everything in a password-protected admin dashboard, can download it as a PDF, and use the dashboard to check classes in on the day.

Why it was built in-house

The website collects children's names, ages, year groups and allergy or health information. Rather than putting that into a third-party sign-up service, Pou Hono keeps all of it in a single database file that sits with the website itself. This is the data sovereignty reason the project exists, and it shaped most of the design decisions in this document. The one outside service it can use is an email provider, which only ever receives the teacher's own name, email address, school name and links (section 6). No child's details are emailed.

The full journey, from a teacher signing up to a class arriving on the day.

2. Gets two linksOn screen and by email: a student link and QR, and a private portal link.
→
3. Students sign upThrough the link or QR, or the teacher adds them. Each picks a workshop.
→
4. Admin sees it allNumbers, filters, chart and PDF. Refresh to see new sign-ups.
→
5. Event dayStaff mark each class Arrived.

Two links, two different codes

When a teacher registers, the website creates two long random codes for the class, one for each link:

LinkWho it is forWhat it can do
…/join/<student code>Students. Share with the class or print as a QR code.Adds a student to that class and shows its school name. It can't open the teacher portal or show student details.
…/register/<teacher code>The teacher only. Do not share.Opens the teacher's class portal: the class list, including allergies, and adding or removing students.

There are no teacher accounts or passwords. Having the teacher code is the permission, so a teacher can start straight away with nothing to set up. The codes are far too long to guess. If a portal link is lost or shared by mistake, an admin can reset it from the dashboard: the old link stops working immediately, and the student link and QR code keep working. (The reset link is shown to the admin to pass on; it is not emailed automatically.)

Individuals

Behind the scenes, everyone who registers as an individual is grouped under one shared record called "Individual / Walk-in". It never appears as a class in the admin table, and it can never open a teacher portal. Individual sign-ups are still counted in the dashboard figures and the chart, and appear in the PDF with "Individual" as their school.

What the admin figures mean

  • Total registrations: the number of classes that have registered (individuals not included).
  • Total students: the expected number of students: each class's booked number minus those not attending, plus individual sign-ups.
  • Most popular session and the pie chart come from the students who have actually signed up, because a workshop is chosen by each student, not by the class.

4Keeping the data safe

The website holds children's personal and health information, so access is deliberately tight.

Who can see what

LevelCanCannot
Public
anyone		Register a class. Sign a student up, if they have a valid student link.See student or teacher details. A student link shows the school name; the home page receives only a count.
Teacher
has a portal link		See and manage their own class only.See or change any other class, or the individual sign-ups.
Admin
has the password		See everything, manage classes, export the PDF.Edit or remove a single student (section 11).

Protections already in place

  • The admin password is never stored. Only a scrambled, one-way version of it is kept (a "bcrypt hash"), so the password can't be read back out of the server's settings.
  • Admin sign-in expires and can be revoked. Each sign-in gets its own random session, recorded on the server, which ends after 8 hours, on logout, or when the admin password is changed. Logging out also clears the dashboard from the screen.
  • Limits on repeated attempts. 10 admin login attempts per 15 minutes and 20 class registrations per hour from one internet address. Student sign-ups allow 100 an hour per class and internet address (60 for individuals), with a ceiling of 600 per address. Teachers can add 200 an hour per class. These slow automated password guessing and junk sign-ups.
  • Codes are never handed out. A class's codes only ever appear inside its own links (on the confirmation screen and in the teacher's email). The one exception is the shared code used for individual sign-ups, which is public by design and can only add a sign-up.
  • Common attacks are blocked. Registration and student fields are checked on the server, with text limits (for example 100 characters for a name and 500 for allergies). Error messages never reveal how the website works inside. Whatever is typed is handled safely, so it cannot be used to tamper with the database (SQL injection) or to run harmful scripts on other people's screens (cross-site scripting). The student consent tick-box is checked on the form, but the website does not keep a record that it was ticked.
  • The PDF export leaves out ages and allergies, and browsers are told not to keep a copy of it. Once downloaded, though, the file is ordinary: store it carefully and delete it when done.
  • Browser protections. The website tells browsers not to pass its addresses on to other sites, not to show it inside other sites, and to limit where scripts can load from. The admin dashboard loads no outside code at all.
  • It fails safe. If the admin password or secret key is missing from the settings, the public pages keep working but the admin dashboard refuses everyone. If email fails, the registration is still saved.

Your responsibilities

  • Keep the admin password to the smallest group that needs it, and change it if someone leaves (section 17).
  • Keep the server settings private. They hold the password hash, the secret key and the email login.
  • Tell teachers their portal link is private. If one is lost or shared, reset it from the dashboard and send the teacher the new one.
  • Treat downloaded PDFs as confidential, and don't email them around.
  • Make sure the hosting is backed up (section 7).

5Going live on Railway, step by step

In one sentence: move the GitHub repository to an SACTH account, deploy it on Railway, and pay for Railway's Pro plan. This section explains why, and gives every step.

5.1 How it runs today

ItemCurrent state (last checked 5 October 2026)
Web addresshttps://pou-hono-site.vercel.app, a free sub-address of Vercel's own domain, which SACTH cannot own.
What works thereOnly the pages display. The server part isn't running, so registering, student sign-up, the teacher portal, admin login and the home page counter all fail. No registration data is stored on Vercel.
Who owns itDeployed from the GitHub repository Melware0-0/PouHonoSite. [confirm the Vercel account and plan with the team member who set it up]
Why not Vercel

Pou Hono keeps all its data in one database file beside the website. Vercel runs server code as short-lived "serverless" functions with no permanent disk, so registrations would fail to save or quietly disappear. Pou Hono needs a server that keeps running, with a permanent disk. Railway provides both.

5.2 Which Railway plan

PlanListed priceWhat matters for Pou Hono
Pro recommended$20 a month, which includes $20 of usageAllows sending email over SMTP, which is how the confirmation email is built today. Volumes start at 50 GB (the database will be a tiny fraction of that).
Hobby$5 a month, which includes $5 of usageBlocks outgoing SMTP email. It would work only if a developer first switches the email to an HTTPS-based provider (section 6.3). Volumes up to 5 GB.
Free / Trial$0Not suitable for the live site: 500 MB volumes, SMTP blocked, and very small usage allowances.

Usage above the included amount is billed on top. Pou Hono is small (one server, one small file), so a modest bill is likely, but set a usage limit or alert in Railway's billing settings. Prices are as listed by Railway; confirm the currency and current figures at sign-up.

Sources, checked 12 October 2026: railway.com/pricing (plans, prices, volume sizes); docs.railway.com/networking/outbound-networking ("SMTP is only available on the Pro plan and above"; "Free, Trial, and Hobby plans must use transactional email services with HTTPS APIs"); docs.railway.com/reference/volumes (default volume sizes).

5.3 Where the data will live

Railway has four regions: US West (California), US East (Virginia), EU West (Amsterdam) and Southeast Asia (Singapore). There is no New Zealand or Australian region, so the data would be held offshore, in Singapore as the nearest. This sits awkwardly with the data-sovereignty reason for building in-house. SACTH should make that call knowingly and say so in its privacy statement. If keeping data onshore is a must, use an NZ or Australian host with a long-running Node.js server and a permanent disk; the steps below still apply in spirit.

Source: docs.railway.com/reference/deployment-regions, checked 12 October 2026. Railway says more regions may be added, so check again before signing up.

5.4 The steps

Steps 1–3 are for SACTH. Steps 4–11 are best done by a developer with SACTH watching, so SACTH knows where everything is.

  1. Create a GitHub organisation for SACTH (free), using a shared SACTH email with at least two SACTH owners. The current owner of Melware0-0/PouHonoSite then uses Settings → Transfer ownership on the repository to move it into that organisation. GitHub redirects the old address. Developers stay on as collaborators. Agree code ownership and licence in writing; the repository has no licence file.
  2. Create the Railway account with the same SACTH email, not a developer's. Add a payment method, choose the Pro plan, and invite developers as members of the workspace.
  3. Decide the web address (5.5), so it is ready for step 9.
  4. New Project → Deploy from GitHub repo, and pick the repository in SACTH's organisation (Railway will ask to connect to GitHub). Railway builds it and starts it with npm start. It reads the Node.js version (22 or 24) from the project's settings file.
  5. Choose the region before adding storage. In the service's settings, set the region (Singapore is nearest). Moving a service with storage between regions later causes downtime while the data is copied.
  6. Add a volume (Railway's word for a permanent disk) to the service, mounted at /data. Run one copy of the service only. Railway does not allow extra copies (replicas) on a service with a volume, and the database is one file in any case.
  7. Set the variables in the service's Variables tab:
    VariableValue
    NODE_ENVproduction
    ADMIN_PASSWORD_HASHThe scrambled admin password. A developer generates it from a new, long password (section 17). Keep the password itself in SACTH's password manager.
    SESSION_SECRETA long random string, generated fresh (section 17).
    DATABASE_PATH/data/pou-hono.db
    TRUST_PROXY1, so the attempt limits see each visitor's real address. Check it after deploying (step 10).
    PUBLIC_BASE_URLThe final address, e.g. https://register.sacth.nz. Every student link, portal link, QR code and email is built from it.
    EMAIL_ENABLED, SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS, MAIL_FROMFrom the email provider (section 6). Leave EMAIL_ENABLED=false until the provider is set up.
    RAILPACK_DEPLOY_APT_PACKAGESfonts-dejavu-core, so the PDF export can print macrons and ʻokina (see the box below).
    PORTDo not set. Railway sets it.
  8. Switch off the demo data before the first real start. On an empty database the website creates five example schools and eighteen example children. Before the first start on Railway, a developer should switch off the two "seed" blocks in db.js and push that change (section 17). This matters because the two example individual sign-ups cannot be removed through the website afterwards (section 11). If the site has already started with demo data, the cleanest fix is to delete the database file on the volume and restart with the seed switched off, while nothing real is in it.
  9. Add the custom domain in the service's Networking settings. Railway shows a CNAME record and a TXT record. Add both at the domain's DNS provider; the domain won't verify with the CNAME alone. Railway then issues the HTTPS certificate automatically. DNS changes can take a while to spread, up to 72 hours. Do this before any real teacher registers, so no one is ever sent a link on a temporary address.
  10. Test end to end on the real domain:
    • Register a test class with your own email address. Check the email arrives (and isn't in spam), and that its links and QR code work.
    • Scan the QR code on a phone and sign up a test student with a macron in the name, e.g. "Tāne Ngāti".
    • Open the teacher portal from the email and check the student is there.
    • Sign in to the admin dashboard, check the figures, export the PDF and check the macron prints correctly.
    • From two different networks (e.g. office wifi and a phone on mobile data), confirm both can register, which shows the attempt limits see real addresses.
    • Delete the test class (this also removes its test student).
  11. Turn on backups (section 7).
  12. Retire the Vercel deployment so it can't be mistaken for the real site.
The PDF export and special characters

The PDF needs a font with Māori and Pasifika characters (macrons such as ā, and the ʻokina). The website looks for one of a few common fonts already on the server. If none is there it falls back to a basic font and those characters print as junk. Railway's servers may not have one. Railway's build system documents the RAILPACK_DEPLOY_APT_PACKAGES variable for adding system packages, and fonts-dejavu-core is the standard package that provides the DejaVu font the website looks for. This has not yet been tried on Railway, so check it: after deploying, the server log must not contain "PDF export: no Unicode font found", and the macron test in step 10 must pass.

Sources, checked 12 October 2026: railpack.com/guides/installing-packages; docs.railway.com/builds/build-configuration.

6Setting up the confirmation email

The email is built and tested. It stays switched off until SACTH has an email provider and has set up its domain.

6.1 What is sent, and to whom

  • Teachers only, straight after they register a class. It contains a greeting, a "save the date" box with their event day and the venue address, the student link and its QR code, their private portal link (with a "keep this to yourself" warning), a line about event-day details, and SACTH's contact email and phone number. It is sent as both a formatted and a plain-text version. A preview is in Appendix A.
  • Students and individuals get no email. Their forms do not ask for an email address, on purpose, to collect as little about children as possible.
  • Email is sent in the background. If it fails, the teacher still sees the confirmation screen with both links, and the failure is written to the server log.
  • While email is switched off, the website writes a copy of each email to the server log instead (leaving out the private portal link). That copy includes the teacher's name and email address, so the hosting logs hold personal details; keep access to them limited.

6.2 Choosing a provider

Any transactional email provider will do: for example Resend (Railway's own suggestion), SendGrid, Postmark or Mailgun, or SACTH's existing email system if it allows sending through "SMTP". Compare their current prices and free allowances yourselves; Pou Hono sends one email per class, so the volume is small. Open the account with the shared SACTH email.

Railway's Hobby plan blocks this kind of email

Pou Hono sends email over SMTP, the standard email-sending method. Railway blocks SMTP on its Free, Trial and Hobby plans; it is available on Pro and above. So there are two options:

  1. Use Railway Pro (recommended in section 5) and any provider's SMTP settings. No code change.
  2. Stay on Hobby and use the provider's web API instead. A developer replaces one small function, sendEmail() in email.js, with the provider's own code (an example for SendGrid is in the comment at the top of that file). Everything else about the email stays the same. Roughly an hour or two of developer time, plus testing.

Source: docs.railway.com/networking/outbound-networking, checked 12 October 2026. Railway also notes that after upgrading to Pro the service must be redeployed before SMTP works.

6.3 Setting up your domain so emails aren't marked as spam

Emails must come from an address on a domain SACTH controls, e.g. noreply@sacth.nz. Email systems check that the sender is allowed to send for that domain. The provider will show you a few DNS records to add, at the same place as the Railway records in section 5:

  • SPF: a public list of which services may send email for your domain.
  • DKIM: a digital signature on each email that proves it really came from you and wasn't changed on the way.
  • DMARC (recommended): tells receiving systems what to do with emails that fail those checks.

Add the records exactly as the provider shows them, then press "verify" in the provider's dashboard. Like the Railway records, they can take a while to take effect. If SACTH's domain already sends email (for example through Microsoft 365 or Google Workspace), whoever manages it should add the provider to the existing SPF record rather than creating a second one.

6.4 The settings

VariableWhat to put

6.5 Testing it

  1. Set the variables above and redeploy.
  2. Register a test class using your own email address.
  3. Check the email arrives, and look in the spam folder too. Open it on a phone and on a computer; check the QR code shows and both links open the right pages.
  4. In Railway's logs, look for [email] Confirmation sent to …. If you see [email] Could not send instead, the line after it says why (usually a wrong password, port or unverified sender).
  5. Delete the test class from the admin dashboard.

6.6 What to personalise before switching it on

A developer edits these in email.js (section 9 has the full list):

  • The event-day details line (detailsPlaceholder). It currently says "Times, what to bring and arrival details will be sent closer to the day." Replace it with real times, what to bring and arrival or parking details once confirmed.
  • The contact email and phone number, which are typed into the email in two places (the formatted and the plain-text versions).
  • The event name (EVENT_NAME), and the wording of the subject line and greeting if wanted.
  • The venue address comes from EVENT_LOCATION in server.js, and the date from public/event-days.js.

7The database: is it big enough?

An honest assessment, because the team asked for this to be flagged.

7.1 What it is

Pou Hono stores everything in SQLite: one database file, read and written by the website itself, with no separate database server. It runs in "WAL" mode, which lets people read while someone else is saving. It is simple, cheap, and keeps the data in one file SACTH controls.

7.2 Will it cope with about 1,000 users?

Very likely yes, on one server with a permanent volume. Each registration or sign-up is one small write taking a tiny fraction of a second, and even a busy period produces a few writes a minute, not thousands a second.

But be clear about three things:

  • It has not been load tested. Nobody has yet sent 1,000 people at the site at once. The likely pinch point is a school assembly where hundreds of students scan the QR code in the same minute. That should be fine, but it should be proven before launch.
  • It limits you to one server. You cannot run two copies side by side for extra capacity or to stay up if one fails; while the server restarts, the site is briefly down.
  • Backups are file copies. There is no managed database service doing it for you; backups have to be set up (7.4).

7.3 When to move to a bigger database

Move to a database server such as PostgreSQL (Railway offers one) if any of these become true:

  • You need more than one copy of the website, or it must stay up through a server failure (high availability).
  • The load test fails and tuning doesn't fix it, or the project grows well beyond this event (many events, many thousands of sign-ups).
  • You want managed backups and point-in-time restore from the provider.

What moving involves: it is a developer task of days, not hours. The database setup in db.js and every database query in server.js (about 20 of them) would need rewriting for a Postgres connection, which also changes how the code waits for answers from the database. Then the data is copied across and everything retested. Doable, but not a settings change; for NZ Tech Week 2027 we don't recommend it unless the load test says otherwise.

7.4 What to do before launch

  1. Run a load test on the Railway deployment before registrations open, simulating hundreds of students signing up within a few minutes. Run it with EMAIL_ENABLED=false, ideally on a separate copy of the site, and delete the test data afterwards. A short developer job.
  2. Turn on daily backups. Railway offers volume backups on a schedule: daily (kept 6 days), weekly (kept 27 days) and monthly (kept 89 days), restored from the service's Backups tab. Check that your plan includes them. Two cautions from Railway's own documentation: backups can only be restored into the same project, and wiping a volume deletes all its backups. (docs.railway.com/reference/backups and /reference/volumes, checked 12 October 2026.)
  3. Also keep copies off Railway. A developer regularly takes a safe copy with sqlite3 /data/pou-hono.db ".backup backup-YYYY-MM-DD.db" (never a plain file copy while the site runs) and stores it, encrypted, somewhere SACTH controls.

8Languages and translations

Visitors pick English, te reo Māori, gagana Sāmoa or lea faka-Tonga from the menu in the header. The choice is remembered on that device.

The translations are drafts and must be checked

All the Māori, Samoan and Tongan text was produced with AI and has not been checked by fluent speakers. It may be wrong, awkward or culturally off. It must be reviewed by someone fluent in each language before the site is used with real families. The warning at the top of public/translations.js says the same and should stay until the review is done.

8.2 Getting them reviewed

  1. Ask a developer to export the strings from public/translations.js into a spreadsheet: one row per string, with English beside each language. There are 117 strings per language.
  2. Give each reviewer the English and their language, plus the screenshots in Appendix A so they see where each string appears. Record their names in section 13.
  3. The developer puts the corrected text back into translations.js, checks each page in each language, and then updates the warning at the top of the file to say who reviewed it and when.

8.3 How it works (for the developer)

  • Each piece of text on a page has a label, e.g. <h1 data-i18n="reg_title">. translations.js holds the text for each label in four blocks: en, mi, sm and to. Placeholders use data-i18n-placeholder; the few strings with formatting (such as the home page heading) use data-i18n-html.
  • Messages that the page's own script shows (e.g. "Submitting…", "Copied!", a success message) use i18nText('key', {name: …}) from the same file.
  • To change a string: edit it in all four blocks. To add one: add the label to the HTML and the key to all four blocks. A key missing from a language shows the English text instead.
  • To add a fifth language (e.g. Cook Islands Māori): add a new block to translations.js with every key, add a line for it to the language menu and to LANG_LABELS in public/nav.js, and get it reviewed like the others.

11Known limitations and recommended next steps

These are the edges of what was in scope, listed so nobody is surprised by them.

Privacy and consent priority

The website collects children's names, ages and health information, which puts it under the NZ Privacy Act 2020. The following are not yet in place:

  • A privacy statement page explaining what is collected, why, who can see it, where it is held (Singapore, if Railway is used), how long it is kept and how to ask for it to be corrected or deleted. The student form has a one-paragraph statement, but there is no full policy.
  • A parent or caregiver consent step. At the moment students agree for themselves, at any age.
  • A retention plan: when the data and any downloaded PDFs and backups will be deleted after the event, and who does it.

We recommend SACTH settle these before registrations open. Building a privacy page and a consent tick-box is a small piece of work once the wording is agreed.

Removing a single student important

  • The admin dashboard cannot edit or remove an individual student. (Version 1.1 of this document wrongly said it could.) Staff can only delete a whole class, which removes all its students.
  • A student in a class can be removed by their teacher, from the teacher portal.
  • An individual sign-up cannot be removed by anyone through the website: individuals have no teacher, and the shared "Individual / Walk-in" record cannot be deleted. This matters if someone asks for their details to be deleted (a privacy request), and it is why the two example individuals must be prevented by switching the demo data off before launch (section 5) rather than removed afterwards.
  • Until an admin "remove student" feature is built (a small job), such requests need a developer to remove the row directly from the database.

Admin dashboard

  • One shared admin password, with no individual staff accounts and no log of who changed what.
  • The PDF export is the only download. There is no spreadsheet (CSV/Excel) export, the PDF ignores the dashboard filters, and there is no printable per-class list with allergies for the day. Teachers can see their own class's allergies in their portal.
  • The PDF font must be checked on the live server (section 5), or names with macrons and ʻokina print incorrectly.
  • The dashboard loads every child's details. To draw its figures it downloads all students, including names and allergies, even though the figures only need ages, year groups and workshops. Trimming this is recommended.
  • Staff can't edit a class's year groups, and teachers can't change their own class details; the portal tells them to contact SACTH.
  • On smaller laptop screens the registrations table scrolls sideways to reach the Status and Actions columns.

Email

  • Only teachers get an email. Students and individuals get none, because no email address is collected.
  • A teacher who loses their portal link can search their inbox for the confirmation email; otherwise an admin resets it and sends the new link by hand.
  • On Railway's Hobby plan, email needs a small code change (section 6).

Other

  • The translations are unreviewed AI drafts (section 8).
  • Attempt limits are kept in memory, so they reset whenever the server restarts.
  • There are no automated tests (changes are checked by hand), and no load test yet (section 7).
  • The home page map loads from Google; it receives no registration data.
  • The demo classes have no year groups recorded, because they were created before the question existed. (The screenshots in Appendix A show example year groups added for illustration.)

Upgrades, renames, the walk-in container and seed data

  • In-place upgrades: db.js runs on every start. not_attending, is_walk_in, teacher_token, token, created_at and year_groups are each added through addColumnIfMissing(...) when absent, so older databases upgrade without being deleted.
  • Workshop rename: on every start, students still holding an old placeholder value are moved to the real workshop: Programming → AI Fundamentals Workshop; Social Media → Graphic Design Workshop; Robotics → Build and Battle Robots Workshop; Computer Building → How to Hack a Bank (Ethical Hacking Workshop); Gaming → DJ'ing Basics Workshop. It is a no-op once done.
  • Walk-in container: created on startup if missing (older databases have their existing "Individual / Walk-in" row marked). It cannot be edited (apart from status) or deleted through the API, so its students cannot be removed through the site.
  • Seed data: on a completely empty registrations table, five example classes are inserted; the eighteen example students (two of them under the walk-in container) are inserted only on that same startup and only if the students table is empty. Real data is never touched.

16Access control and API reference

Every route sits behind exactly one of three gates. When adding a route, decide its gate first.

  • Public No credentials.
  • Teacher requireTeacherToken reads the teacher token from Authorization: Bearer <token> or ?token=, looks it up by teacher_token only, loads that registration into req.registration, and scopes queries to it. A missing, unknown, student or walk-in token all return the identical 404.
  • Admin requireAdmin checks the signed, httpOnly cookie pou_hono_admin (SameSite=Lax, Secure when NODE_ENV=production). Its value is a session id that must exist in admin_sessions, be unexpired, and match the current password fingerprint.

Page routes

/join/:token (student token) serves student.html. /register/:token (teacher token) serves teacher.html. An unknown token on either, including a student token on /register/, redirects to /; a teacher credential somehow on the walk-in container gets a plain 404. Every other page is served statically from public/.

Cross-cutting behaviour

Every response carries Referrer-Policy: no-referrer, X-Content-Type-Options: nosniff, X-Frame-Options: DENY and a Content-Security-Policy. /api responses are Cache-Control: no-store. Unknown /api paths return a JSON 404. A final error handler returns a generic JSON message (413 for oversized bodies) and never a stack trace. Share and portal links use PUBLIC_BASE_URL when set.

Rules that must not be broken

  • Never build SQL by string concatenation. External values are bound using db.prepare(...) with ? or named placeholders. Only trusted, code-defined column lists and migration identifiers are interpolated.
  • Select explicit columns from registrations (see REGISTRATION_COLUMNS), never SELECT *, so a new column can't leak. teacher_token and token must never be added to it.
  • The walk-in container is identified by is_walk_in via isWalkInRegistration(), never by its school name, and must never pass requireTeacherToken.
  • In the front end, every user-supplied value inserted with innerHTML goes through the page's escapeHtml helper, or is set with textContent. The pages' escapeHtml does not escape quotes, so it must not be used inside HTML attributes. (email.js has its own, which does.)
  • Email must never be awaited by a route, and must never include children's details.

Routine tasks

  • Change the admin password: generate a new hash, replace ADMIN_PASSWORD_HASH, restart. Every existing admin session ends.
  • Rotate the cookie secret: replace SESSION_SECRET and restart. This also signs everyone out.
  • A teacher has lost or leaked their portal link: use Reset teacher link on their class and send them the new link.
  • Disable demo data for launch (do this before the first production start): in db.js, stop the class seed (the if (rowCount === 0) { … } block) and the student seed (the if (seededRegistrationIds && studentCount === 0) { … } block) from running, e.g. by changing each condition to false, then push. Deleting pou-hono.db alone does not give an empty site: on restart db.js sees an empty table and seeds again. Deleting the five demo classes in the dashboard removes their students, but the two demo individuals under the walk-in container cannot be removed through the site; if they exist, either delete the database file (with its -wal and -shm files) while it holds nothing real and restart with the seed disabled, or remove those two rows directly with SQL.
  • A privacy deletion request for one student: a class student can be removed by the teacher in their portal. An individual (walk-in) student needs a developer to run, against the live database, DELETE FROM students WHERE id = ? with the right id (find it with a SELECT on name). Take a backup first.
  • Reset everything (development only): stop the server and delete the database file with its -wal and -shm files. The next start rebuilds the schema and the demo data.
  • Back up: don't copy the file while the server runs (WAL mode). Use sqlite3 /data/pou-hono.db ".backup backup-YYYY-MM-DD.db", or Railway's volume backups (section 7). Keep copies off the server, encrypted.

BEvent-day check-in guide for staff

One page for whoever is on the door. Print it out for the day.

Before the day

  1. Make sure you can sign in: go to [live website address]/admin.html and enter the admin password.
  2. Check the Notes column for anything you need to prepare, such as wheelchair access or language support.
  3. If you want a paper list of names, use Export PDF. It has no allergies; ask teachers to bring their class list from their portal, which shows each student's allergies and health notes.

When a class arrives

  1. Type the school name into Search by school name.
  2. If the school has more than one booking, check the Event day column to find today's.
  3. Click the yellow Pending label. It turns green and reads Arrived. Click it again to undo a mistake.

Useful views

  • Who hasn't arrived yet? Set the status filter to Pending.
  • A class that never registered? Register them on the spot through the normal Register page, then mark them Arrived.
  • Numbers changed at the door? Click Edit on the class, correct the student or adult numbers, and save.
  • Clear filters resets the view.
Remember
  • Sign-in lasts up to 8 hours. If the dashboard asks for the password again, sign in again; nothing is lost.
  • Delete removes a class and all its students permanently. You don't need it on the day.
  • Printed or downloaded lists contain children's names: collect them at the end of the day.
  • Log out on shared computers when you're done.
