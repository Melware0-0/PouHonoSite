1Summary

Pou Hono is the registration website for NZ Tech Week 2027, run by SACTH and The Cause Collective for South Auckland schools, youth groups and individuals.

A teacher registers their class and is given two things: a link and QR code to share with their students, and a private link to their own class portal. Students open the shared link and register themselves, and they are grouped under their teacher's class automatically. Teachers can also type students in themselves. Individuals who are not part of a school group can register on their own. SACTH staff see everything in a password-protected admin dashboard and use it to check classes in on the day.

Why it was built in-house

The website collects children's names, ages, year groups and allergy or health information. Rather than putting that into a third-party sign-up service, Pou Hono keeps all of it in a single database file that sits with the website itself. Nothing is sent to an outside data service. This is the data sovereignty reason the project exists, and it shaped most of the design decisions in this document.

About this version

A security and functional review on 5 October 2026 found and fixed 15 issues, plus one tidy-up. The fixes are on separate branches on GitHub, waiting for the development team to review and merge them (section 15). This document describes the website with those fixes merged.

3How it works

The full journey, from a teacher signing up to a class arriving on the day.

→
2. Gets two linksA student link and QR to share, and a private portal link.
→
3. Students sign upThrough the link or QR, or the teacher adds them.
→
4. Admin sees it allNumbers, filters and the session chart. Refresh to see new sign-ups.
→
5. Event dayStaff mark each class Arrived.

Two links, two different codes

When a teacher registers, the website creates two long random codes for the class, one for each link:

LinkWho it is forWhat it can do
…/join/<student code>Students. Share with the class or print as a QR code.Adds a student to that class and shows its school name. It can't open the teacher portal or show student details.
…/register/<teacher code>The teacher only. Do not share.Opens the teacher's class portal: the class list, including allergies, and adding or removing students.

There are no teacher accounts or passwords. Having the teacher code is the permission, so a teacher can start straight away with nothing to set up. The codes are far too long to guess. If a portal link is lost or shared by mistake, an admin can reset it from the dashboard: the old link stops working immediately, and the student link and QR code keep working.

Individuals

Behind the scenes, everyone who registers as an individual is grouped under one shared record called "Individual / Walk-in". It never appears as a class in the admin table, and it can never open a teacher portal. Individual sign-ups are still counted in the dashboard figures and the session chart.

What the admin figures mean

  • Total registrations: the number of classes that have registered (individuals not included).
  • Total students: the expected number of students: each class's booked number minus those not attending, plus individual sign-ups.
  • Most popular session and the pie chart come from the students who have actually signed up, because a session is chosen by each student, not by the class.

4Keeping the data safe

The website holds children's personal and health information, so access is deliberately tight.

Who can see what

Protections already in place

  • The admin password is never stored. Only a scrambled, one-way version of it is kept (a "bcrypt hash"), so the password can't be read back out of the server's settings.
  • Admin sign-in expires and can be revoked. Each sign-in gets its own random session, recorded on the server, which ends after 8 hours, on logout, or when the admin password is changed. A copied sign-in stops working at that point too. Logging out also clears the dashboard from the screen.
  • Limits on repeated attempts. 10 admin login attempts per 15 minutes and 20 class registrations per hour from one internet address. Student sign-ups allow 100 an hour per class and internet address (60 for individuals), with a ceiling of 600 per address. Teachers can add 200 an hour per class. These slow automated password guessing and junk sign-ups.
  • Codes are never handed out. A class's codes only ever appear inside its own links. The one exception is the shared code used for individual sign-ups, which is public by design and can only add a sign-up.
  • Common attacks are blocked. Registration and student fields are checked on the server, with text limits (for example 100 characters for a name and 500 for allergies). Error messages never reveal how the website works inside. Whatever is typed is handled safely, so it cannot be used to tamper with the database (SQL injection) or to run harmful scripts on other people's screens (cross-site scripting). The student consent tick-box is checked on the form, but the website does not keep a record that it was ticked.
  • Browser protections. The website tells browsers not to pass its addresses on to other sites, not to show it inside other sites, and to limit where scripts can load from; inline scripts and one outside script source are still allowed. The admin dashboard loads no outside code at all.
  • It fails safe. If the admin password or secret key is missing from the settings, the public pages keep working but the admin dashboard refuses everyone. It never falls open.

Your responsibilities

  • Keep the admin password to the smallest group that needs it, and change it if someone leaves (Part B, section 13).
  • Keep the server settings file (.env) private. It holds the password hash and the secret key.
  • Tell teachers their portal link is private. If one is lost or shared, reset it from the dashboard and send the teacher the new one.
  • Make sure the hosting you choose is secure and backed up (section 5).

The site is online at a free Vercel address, but only the pages are live: registrations can't work there. This section explains the current setup, where to move it, and every account SACTH needs to own.

Why Vercel can't simply be switched on for registrations

Pou Hono keeps all its data in one database file beside the website. Vercel runs server code as short-lived "serverless" functions on a read-only file system. The only writable space is temporary, gets wiped, and isn't shared between copies of the site. So even with the server part enabled, registrations would fail to save or quietly disappear. Vercel says this in its own guidance on SQLite. Vercel suits the pages, not the data. (Provider details in this section are from vercel.com/docs, docs.railway.com, internetnz.nz and docs.github.com, October 2026; confirm before signing up.)

5.2 What the website needs from a host

☐A Node.js server that keeps running (version 22 or 24), not serverless functions.
☐Permanent disk storage (a "volume") that survives restarts and redeployments, for the database file.
☐HTTPS and a custom domain name.
☐Private settings (environment variables) for the admin password hash and secret key.
☐Backups of the volume, or a way to copy the database file off regularly.
☐Ideally: servers in New Zealand or Australia, in line with the data-sovereignty goal.

5.3 Recommended: move to Railway

Railway runs Pou Hono as it is, with a permanent volume, HTTPS and custom domains built in. Its nearest region is Singapore; it has no NZ or Australian region, so the data would be held offshore. If keeping data onshore is a must, use any NZ or Australian host that meets 5.2; the same steps apply.

  1. SACTH creates the Railway account with an organisation email (not a developer's) and adds a payment method. A paid plan is needed for an always-on service with a volume. Invite developers as members.
  2. New project → Deploy from GitHub repo, choosing the repository after it has moved to SACTH's GitHub (5.4). Railway runs npm start.
  3. Add a volume to the service, mounted at /data. Choose the Singapore region before adding it, because moving a volume between regions later causes downtime. Run a single instance: the database is one file.
  4. Set the variables: NODE_ENV=production, ADMIN_PASSWORD_HASH, SESSION_SECRET, DATABASE_PATH=/data/pou-hono.db, TRUST_PROXY=1, and PUBLIC_BASE_URL=https://<your domain>. Generate the hash and secret fresh (section 13). The last three come from the fix branches in section 15. After deploying, confirm the rate limits see real visitor addresses. Let the host set PORT.
  5. Clear the demo data before the first real start (section 13).
  6. Add the custom domain in the service's networking settings. Railway shows a CNAME and a TXT record. Add both at the domain's DNS provider; the domain won't verify with the CNAME alone. Railway then issues the HTTPS certificate automatically, though DNS changes can take up to 72 hours.
  7. Test end to end on the real domain: register a test class, scan its QR code on a phone, sign up a student, check the teacher portal and admin dashboard, then delete the test class.
  8. Retire the Vercel deployment so it can't be mistaken for the real site.

7Known limitations and recommended next steps

These are the edges of what was in scope, listed so nobody is surprised by them.

Privacy and consent priority

The website collects children's names, ages and health information, which puts it under the NZ Privacy Act 2020. The following are not yet in place:

  • A privacy statement page explaining what is collected, why, who can see it, how long it is kept and how to ask for it to be corrected or deleted. The student form has a one-paragraph statement, but there is no full policy.
  • A parent or caregiver consent step. At the moment students agree for themselves, at any age.
  • A retention plan: when the data will be deleted after the event, and who does it.

We recommend SACTH settle these before registrations open. Building a privacy page and a consent tick-box is a small piece of work once the wording is agreed.

Admin dashboard

  • No export or print view. There is no CSV or Excel download, and no printable class list with allergies for the day.
  • One shared admin password, with no individual staff accounts and no log of who changed what.
  • The dashboard loads every child's details. To draw its figures, the dashboard downloads all students, including names and allergies, even though the figures only need ages, year groups and sessions. Trimming this is recommended once the admin student-editing feature is finalised, since that feature may rely on it.
  • On smaller laptop screens the registrations table scrolls sideways to reach the Status and Actions columns.

Teachers

  • Teachers cannot change their own class details after registering. The portal tells them to contact SACTH, and an admin makes the change.
  • A teacher who loses their portal link has to ask SACTH, and an admin resets it. There is no "email me my link", because confirmation emails are not part of this project (section 8).

Other

  • The home page map loads from Google; it receives no registration data. Everything else, including the admin chart library, is served from the website itself.
  • Attempt limits are kept in memory, so they reset whenever the server restarts.
  • There are no automated tests (changes are checked by hand), and no load testing yet (section 8).

Upgrades, the walk-in container and seed data

  • In-place upgrades: db.js runs on every start. The not_attending, is_walk_in and teacher_token columns are in the CREATE TABLE and added through addColumnIfMissing(...); the admin_sessions table is created if missing. Main does not yet migrate databases missing token; that fix is on schoolsearch. Review that migration before starting against a very old database.
  • Walk-in container: created on startup if missing. Older databases that predate the is_walk_in flag have their existing "Individual / Walk-in" row marked automatically. The container cannot be edited (apart from status) or deleted through the API.
  • Seed data: on a completely empty database, five example classes and eighteen example students are inserted. Real data is never touched. To start clean for production, see section 13.

12Access control and API reference

Every route sits behind exactly one of three gates. When adding a route, decide its gate first.

  • Public No credentials.
  • Teacher requireTeacherToken reads the teacher token from Authorization: Bearer <token> or ?token=, looks it up by teacher_token only, loads that registration into req.registration, and scopes queries to it. A missing, unknown, student or walk-in token all return the identical 404.
  • Admin requireAdmin checks the signed, httpOnly cookie pou_hono_admin (SameSite=Lax, Secure when NODE_ENV=production). Its value is a session id that must exist in admin_sessions, be unexpired (8 hours), and match the current password fingerprint. It is set after a bcrypt compare in POST /api/admin/login.

Page routes

/join/:token (student token) serves student.html. /register/:token (teacher token) serves teacher.html. An unknown token on either, including a student token on /register/, redirects to /. The public walk-in token on /register/ redirects home too; a teacher credential wrongly assigned to that container gets a plain 404. Every other page is served statically from public/.

Cross-cutting behaviour

Every response carries Referrer-Policy: no-referrer, X-Content-Type-Options: nosniff, X-Frame-Options: DENY and a Content-Security-Policy. /api responses are Cache-Control: no-store. Unknown /api paths return a JSON 404. A final error handler returns a generic JSON message (413 for oversized bodies) and never a stack trace. Share and portal links use PUBLIC_BASE_URL when it is set.

Rules that must not be broken

  • Never build SQL by string concatenation. External values are bound using db.prepare(...) with ? or named placeholders. Fixed queries may have no parameters; schema SQL uses db.exec. Only trusted, code-defined column lists and migration identifiers are interpolated.
  • Select explicit columns from registrations (see REGISTRATION_COLUMNS), never SELECT *, so a new column can't leak.
  • The walk-in container is identified by is_walk_in via isWalkInRegistration(), never by its school name, and must never pass requireTeacherToken.
  • In the front end, every user-supplied value inserted with innerHTML goes through the page's escapeHtml helper, or is set with textContent. escapeHtml does not escape quotes, so it must not be used inside HTML attributes.
  • The student token must never grant teacher access, and teacher_token must never be added to REGISTRATION_COLUMNS.

13Setup, configuration and operations

Run it locally

npm install                 # Node.js 22 or 24 (20 and 22–26 supported; not 18 or 21)
cp .env.example .env        # Windows: copy .env.example .env, then fill in the values below
node server.js              # or: npm start   →  http://localhost:3000

Settings (.env or the host's environment variables)

VariableValue
ADMIN_PASSWORD_HASHbcrypt hash of the admin password. Generate it with:
node -e "console.log(require('bcryptjs').hashSync(process.argv[1], 10))" 'NewPassword'
SESSION_SECRETLong random string that signs the admin cookie. Generate it with:
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
PORTOptional. Defaults to 3000. Most hosts set this automatically.
NODE_ENVSet to production on the live server, which makes the admin cookie HTTPS-only.
DATABASE_PATHOptional. Where the database file lives. Default: next to db.js. On a host, use the persistent volume, e.g. /data/pou-hono.db; its folder must exist.
TRUST_PROXYOptional. Set when running behind a host's proxy so rate limits see real visitor addresses: a hop count such as 1, or an Express trust-proxy value. Match the proxy layout; trusted proxies must overwrite forwarding headers.
PUBLIC_BASE_URLOptional. The canonical address used to build share links, portal links and QR codes, e.g. https://register.sacth.nz. Unset uses the request's own address.

If either secret is missing, the server starts with a warning and admin login refuses every attempt.

Routine tasks

  • Change the admin password: generate a new hash, replace ADMIN_PASSWORD_HASH, restart. Every existing admin session ends automatically.
  • Rotate the cookie secret: replace SESSION_SECRET and restart. This also signs everyone out.
  • A teacher has lost or leaked their portal link: in the dashboard, use Reset teacher link on their class and send them the new link.
  • Clear demo data for launch: note that deleting pou-hono.db does not give an empty site. On restart, db.js sees an empty database and inserts the demo data again. Either (a) recommended: disable the two seed blocks in db.js before the production server's first start, or (b) on the live site, delete the five example classes in the admin dashboard (which removes their students) and remove the two example individual sign-ups. The class seed runs only when the registrations table has zero rows; the retained walk-in container prevents reseeding even before real classes exist. The student seed also requires classes to have been seeded on that same startup and an empty students table.
  • Reset everything (development only): stop the server and delete the configured database file (default: pou-hono.db) together with its -wal and -shm files. The next start rebuilds the schema and the demo data.
  • Back up: the whole system's data is the one database file. Because it runs in WAL mode, don't just copy pou-hono.db while the server is running. Either stop the server first, or take a consistent copy with sqlite3 pou-hono.db ".backup backup-YYYY-MM-DD.db". Use the configured database path. Schedule daily during registration; keep copies off the server.

BEvent-day check-in guide for staff

One page for whoever is on the door. Print it out for the day.

Before the day

  1. Make sure you can sign in: go to [live website address]/admin.html and enter the admin password.
  2. Check the Notes column for anything you need to prepare, such as wheelchair access or language support.
  3. Ask teachers to bring their own class list. Their portal shows each student's allergies and health notes.

When a class arrives

  1. Type the school name into Search by school name.
  2. If the school has more than one booking, check the Event day column to find today's.
  3. Click the yellow Pending label. It turns green and reads Arrived. Click it again to undo a mistake.

Useful views

  • Who hasn't arrived yet? Set the status filter to Pending.
  • A walk-in class that never registered? Register them on the spot through the normal Register page, then mark them Arrived.
  • Numbers changed at the door? Click Edit on the class, correct the student or adult numbers, and save.
  • Clear filters resets the view.
Remember
  • Sign-in lasts up to 8 hours. If the dashboard asks for the password again, sign in again; nothing is lost.
  • Delete removes a class and all its students permanently. You don't need it on the day.
  • Log out on shared computers when you're done.
